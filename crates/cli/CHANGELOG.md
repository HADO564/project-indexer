# Changelog — dexily

All notable changes to the Project Indexer command-line tool are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and
versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

The CLI is released independently of the desktop app, under tags of the form
`dexily-v<version>`. The app's changes are in the root
[`CHANGELOG.md`](../../CHANGELOG.md).

## [Unreleased]

### Added

- **The TUI now deletes, behind a `y/N` gate.** `d` (untrack), `x` (purge) and `group delete` ask `Stop tracking this project? … [y/N]` on the status line first; only `y` runs it, and any other key cancels, so nothing is deleted by accident. This matches the shell, which already confirms the same three. (Previously these were blocked in the TUI.)
- **Scan a folder from the TUI.** `s` opens a dialog for a folder to scan; type a path (or `.` for the current directory) and `Enter` runs `scan … --import`, so the projects it finds are tracked and appear in the list at once. (A folder picker to browse to the directory is coming next.)

## [0.2.0] — 2026-10-19

### Added

- **A terminal UI: a bare `dexily` opens a full-screen browser of your projects.** A sidebar of views (All, Favourites, Bin) and groups (Ungrouped, then your groups, each with a count), the project list, and the selected project's detail. Navigate with `j`/`k` and the arrows, `g`/`G` for the ends, `Tab` to toggle the sidebar and the list, `h`/`l` pane by pane, and `[`/`]` between the sidebar sections. A `:` command line runs the same commands the shell does (`:favorite app`, `:edit app --name "New"`), showing the result on a message line and refreshing the panes. Letter shortcuts act on the selection — `o` open, `f` favourite/unfavourite, `e` edit, `d` untrack, `r`/`x` restore/purge in the bin — a `Space` action menu lists them, and `?` shows a help overlay. Icons and colours follow `config icons` and each project's mark; `NO_COLOR` is honoured. (Confirming a destructive command and opening the edit form inside the TUI are not wired yet — they say so — and search and live refresh are still to come.)
- **The observer: `dexily mkdir <folders…>` runs the real `mkdir`, then tracks each folder it made.** The command runs exactly as if typed — its own output, prompts and exit code, which always wins; a signal is reported as 128 + its number, an exit code above 255 (Windows) as 1, and Ctrl+C is left to the command while it runs. Every folder named that the command actually created is tracked under its real path: not the parents `-p` makes on the way, not `-m`'s value, not a folder that was already there (a folder named twice is one), and nothing at all when the command failed (`dexily: mkdir failed (exit 1), nothing tracked`) or exited 0 without making anything (`dexily: mkdir made nothing new, nothing tracked`).
- **`dexily git init [dir]` and `dexily git clone <repo> [dir]` track the repository they leave.** `git init` is the working folder or the one named, and `-C <path>` moves the folder git works in; `git clone` is the folder named, or the one git names from the address. The proof is a `.git` in the folder, which may have been there already, so `git init` run again in a repository still tracks it; `--bare` and `--mirror` run but track nothing. The project is named as the app names one: after its remote's repository if it has one, else its folder, and a taken name is qualified with its parent. Only those two git commands run — `dexily git push` is refused before it starts.
- A folder that was already tracked is not asked about or created again: `dexily mkdir app`, then `dexily git init` inside it, is one project, whose trackers are detected again (`dexily: "app" was already tracked; detected its trackers again`). Flags still apply to it, and add to its tags and properties rather than replace them.
- Unreal needs no command of its own — its projects are made in the editor. The detectors look inside whichever folder is tracked, so `dexily git clone` of an Unreal project comes out with both the git and the Unreal tracker.
- A prompt for each folder made, `dexily: track "thing" at …? [Y/n/e]`: Enter or `y` tracks it, `n` leaves an ordinary folder, and `e` tracks it and opens the full edit form (Esc there keeps the project). There is no prompt with `--yes`, under `--json`, with project flags, or when stdin or stderr is not a terminal; dexily then tracks and prints `dexily: tracking "thing" at …` on stderr. `-q/--quiet` hides dexily's own lines, never a warning. Ctrl+C at the prompt ends dexily (130).
- Flags before an observed command set the new project up in the same breath: `dexily --add-tag rust --group Work --notes "demo" mkdir thing`. They are `edit`'s field flags with its rules — `--name` (for a command making one folder; the name must be free), `--description`, `--add-tag`, `--set k=v`, `--notes`, `--open-with`, `--group`, `--color`, `--icon` — and all are checked before the command runs: one that does not check out is a usage error, exit 2, and the command never starts. Everything after the command's name belongs to the command. `--set` names match ignoring case, as `edit --set`; `--group ""` is a usage error, a new project being in no group to begin with. Before one of dexily's own commands they are a usage error.
- If a folder was made but could not be recorded, the command's exit code stands and dexily prints `could not track "thing": <why>` with the `dexily add <folder>` that retries it — even under `--quiet`. If it was tracked but its details — the flags, the form — could not be saved, the message says so instead (`tracked "thing", but could not save its details: <why>`, with the `dexily edit "thing"` that sets them), and under `--json` the project stays in `tracked`.
- `--json` with an observed command prints one line on **stderr**, last, since the command owns stdout: `{"schema":1,"data":{"exit_code":0,"tracked":[…],"failed":[…]}}`. No prompt and no prose.
- On Windows, `mkdir` and `md` are built into `cmd`, so they run through `cmd.exe /D /V:OFF /C`, with `cmd.exe` taken by its full path; an argument containing a character `cmd` would act on (`& | < > ^ % "`) is refused before anything runs.
- **`dexily show <project>` lists the project's own fields.** Beyond name, directory, id, group, colour and icon, the detail view now shows description, tags, properties (one per line, aligned), notes, open-with, favourite, and the created / updated / last-opened dates — each only when the project has it. `--json` still carries every field.
- **More scaffolding recognizers: `dexily cargo new` / `cargo init`, `dexily go mod init` and `dexily gh repo create`.** Each runs the real command, then tracks the project it leaves — `cargo new <path>` the new folder, `cargo init` / `go mod init` the folder that gains a `Cargo.toml` / `go.mod`, and `gh repo create <name> --clone` the folder gh clones the new repository into (proven by a `.git`, as `git clone` is; without `--clone` nothing lands locally, so nothing is tracked). Fail-closed like git: only options dexily models are passed on, anything else is refused before the command runs.
- **Package-manager `init` recognizers — `npm`, `pnpm`, `yarn` and `poetry`.** A **bare** `npm init` / `pnpm init` / `yarn init` (writing a `package.json`) or `poetry init` (a `pyproject.toml`) is observed and tracked. Only the bare form: `npm init <initializer>` / `yarn init <pkg>` downloads and runs a package (`npm init vite` is `npx create-vite`), so a line with a positional is refused — the allowlist's "no downloaded code" guarantee is kept. **`uv init [path]`** is also recognised; uv's positional is the project folder (not a downloaded package, as npm's is), so it is passed on and tracked like `cargo init`. (`pip` itself has no project-init command, so none is recognised for it.)
- **`flutter create`, `deno init` and `zig init` recognizers**, each tracking the project folder it scaffolds (proven by a `pubspec.yaml`, `deno.json` or `build.zig`). The full, maintained list of every recognized command and detected project type now lives in [`docs/cli/SUPPORTED-COMMANDS-AND-PROGRAMS.md`](../../docs/cli/SUPPORTED-COMMANDS-AND-PROGRAMS.md), linked from the observer section of the README.
- **`git worktree add <path>` recognizer** — the observer runs it and tracks the new working tree it checks out (proven by its `.git`, like `git clone`). Fail-closed options; every other `git worktree` form (`list`, `remove`, …) is refused as unknown.
- **Ten more project-type detectors** — CMake (`CMakeLists.txt`), Maven (`pom.xml`), Gradle (`build.gradle`/`.kts`), Docker (`Dockerfile`/`compose`), PHP (`composer.json`), Ruby (`Gemfile`), Dart (`pubspec.yaml`), Swift (`Package.swift`), Elixir (`mix.exs`) and .NET (`*.csproj`/`*.sln`/`global.json`), joining git, Unreal, Node, Python, Go, Godot, Unity and Rust. The full table is in [Supported commands and programs](../../docs/cli/SUPPORTED-COMMANDS-AND-PROGRAMS.md).
- **`-v`/`--verbose` (and `RUST_LOG`)** surface the scan and detector diagnostics now routed through the `log` facade (an unreadable directory, a detector that errored) on stderr — silent by default, so a plain run and `--json` are unchanged.
- **New project-type detectors.** Beyond git and Unreal, a tracked folder is now recognised as **Node** (`package.json`), **Python** (`pyproject.toml` / `setup.py`), **Go** (`go.mod`), **Godot** (`project.godot`), **Unity** (`ProjectSettings/ProjectVersion.txt`) or **Rust** (`Cargo.toml`) — detected wherever a folder is tracked (`add`, `scan`, `git clone`, `mkdir`), each surfaced in `list` / `show` columns and detail, and in `--json` as its own `kind`.
- **`dexily config track-prompt [on|off] [--reset]`** turns the observer's `[Y/n/e]` track prompt off, for someone who always wants auto-track. Off, an observed command tracks and prints `tracking "…"` without asking (as `--yes` does). Saved in `cli-settings.json`; a broken or missing settings file falls back to prompt-on.

### Changed

- **An overridden recognized-git line now tracks the repo it makes.** When a person at a terminal overrides a refused `git init` / `git clone` (refused only over an option), dexily forms the expectation it had already parsed and tracks the repository, applying the project flags — rather than tracking nothing. An overridden *unknown* command still tracks nothing (there is no recognizer to know what it made), and the override is still terminal-only, so the allowlist guarantee is unchanged.
- `edit --color` now points at the right palette when the value typed is a *terminal* colour (one of `config folder-color`'s larger set, such as `red`) rather than a project colour, instead of refusing it with no hint. A genuine typo still gets the plain error.
- **`-h` is now a concise summary; `--help` keeps the full detail.** Each command's and flag's help was one long paragraph, shown in full by both `-h` and `--help`. The first line is now a short description — so `dexily <cmd> -h` and the command list read at a glance — and the elaboration (rules, examples, caveats) stays under `--help`. `scan --import`, which had no help text at all, now describes itself. The complete reference is the new [manual](../../docs/cli/MANUAL.md) (#35).

### Fixed

- A no-op `edit` — a field flag set to the value the project already holds — writes nothing and reports `nothing changed`, as a form saved untouched already did, instead of moving `updated_at` for a change that never happened.
- `dexily scan <dir>` on a path that does not exist, or is a file, is now an error (exit 1), as `add` is for a missing directory, rather than reporting `0 found` with exit 0 as if the folder held no projects. An unreadable *sub*directory met mid-walk is still skipped, never fatal.
- Scan and detector diagnostics (an unreadable directory, a detector that errored) no longer print prose to stderr during a run; they go through the logging facade, so a `--json` run's stderr stays clean. (These messages came from `dexily-core`.)

### Security

- **dexily only runs commands it has a recognizer for** — today `mkdir`, `git init` and `git clone`. Anything else, any other git command and a path to another program named `mkdir` included, is refused before it starts (``dexily: `git push` isn't a command dexily observes (it knows: mkdir, git init, git clone). Run it directly.``, exit 2), so a script or an agent given dexily cannot use it to run arbitrary programs. Arguments are handed to the command as a list, never joined into a line for a shell.
- **A refusal can be overridden only by a person at a terminal.** When dexily refuses a command, someone who typed it is shown the reason and asked `run it anyway? [y/N]`; a deliberate yes runs the command untouched and tracks nothing it makes. The default is no, `--yes` never reaches the prompt, and a pipe, a script, a redirected stream and `--json` are never asked — they get the refusal and its reason, exit 2, as before. The guarantee that a script or an agent cannot use dexily to run arbitrary programs is unchanged; only a human at their own keyboard may set a single refusal aside.
- **A git line runs only if dexily knows every word of it.** Only the options dexily lists are passed on to `git init` and `git clone`, each spelled in full and given one at a time — before the subcommand `-C <path>`, `--no-pager`, `--version` and `--help`, and each subcommand's everyday options (`-q`, `-b <name>`, `--depth <n>`, `--recurse-submodules`, …; the full list is in `docs/cli/agents.md`). Anything else is refused before git starts, exit 2: an abbreviation (`--dep 1`, `--upl=…`), short options run together (`-qb main`, `-j4`), a global option dexily does not know (`--git-dir`, `--work-tree`, `--shallow-file`), or any option git adds later. Git takes more spellings than any list of bad options can hold — any unique abbreviation of a long option, short options run together, global options whose value is the next word (which turns `init` into a file name and the word after it into the real subcommand) — and each of those once ran another program. The options that run a program — `-c` / `--config` (a setting can name one, as `core.sshCommand` does), `--config-env`, `--exec-path`, `-u` / `--upload-pack`, `--template`, whose hooks would run — are in no list and say why: `` `--upload-pack` makes git run another program, so it is not passed on. Run git directly. `` So do the `ext::` and `fd::` addresses, bare clone or not. Since what each option takes is known, a value is never read as the repository or the folder.

## [0.1.0] — 2026-10-08

The first release, as `dexily`: on crates.io (`cargo install dexily`), and as
archives for macOS, Linux (static) and Windows with `curl | sh` and PowerShell
installers on the GitHub release.

### Changed

- The command is now `dexily`, its chosen name; `indexer` was a placeholder. Messages start `dexily:` too. The crates are renamed with it: the CLI is the `dexily` crate (`cargo run -p dexily`, `cargo install dexily`) and the shared core is `dexily-core`, whose library is still `indexer_core`. The settings and the shared database are where they were.

### Added

- `dexily group list|create|edit|delete` manages groups from the command line, as the app's group manager does. `group list` shows each group's name, colour, icon and how many projects it holds. `group create <name>` adds one last in the sidebar, `cyan` with the `briefcase` icon unless `--color` or `--icon` say otherwise; `group edit <group>` renames it (`--name`) or changes its colour or icon; `group delete <group>` asks first and leaves its projects ungrouped. A group's icon is one of the bundled ones, as in the app. A project still joins a group with `edit --group`.
- `dexily config icons nerd|emoji|off` draws each project's and group's icon before its name in `list`, `show` and `group list`: Nerd Font glyphs (which need a Nerd Font in the terminal), emoji, or none — the default, since no program can tell which font a terminal has. A project without an icon shows the folder, as in the app, and so does a custom icon, an image no terminal can draw. Icons appear only on a terminal: piped, a name is just the name.
- Names in `list`, `show` and `group list` are drawn in the project's own colour, or else its group's, as its mark is in the app; `show` also prints the project's colour and icon, and its group in the group's colour. Off when piped or under `NO_COLOR`.
- `dexily edit <query> --full` opens the form with every field the app's edit view has, in the app's order: name, directory, description, tags, a favourite checkbox (Space ticks it), notes, open with, group, colour, icon, then the properties. The group is chosen rather than typed — ←/→ step through "Ungrouped" and then each group, wrapping at the ends as Tab does — and the form's frame and title take the project's colour, as its tile does in the app, following the colour box as you type, with a swatch beside it — so a colour is previewed before it is saved (none under `NO_COLOR`). A directory, colour or icon that cannot be saved keeps the form open with `Not saved:` and the reason in place of the key hints, so nothing else typed is lost; the next key carries on editing. The title says `· all fields`, so the two forms cannot be mistaken for each other. `--full` only chooses the form: beside a field flag, piped, or under `--json`, it is a usage error.
- Every field in the full form has its `edit` flag too, so nothing is editable only in the form: `--name` renames a project; `--directory` points it at another folder after a move on disk (made absolute, it must exist, and its trackers are detected again); `--notes`; `--open-with`, stored as typed less surrounding spaces and checked only when you `open`; `--group <name>`, matched ignoring case, moves the project into a group, and `--ungroup` (or `--group ""`) takes it out; `--color`, a palette name or `#rrggbb`; and `--icon`, a bundled icon or `custom:<name>` for one added in the app. An empty value clears notes, open with, colour and icon. A name, folder or group that is already taken or does not exist, and a colour or icon that is not one, is refused with the choices rather than stored — so a typo never quietly saves.
- An `edit` that would change nothing writes nothing and says `nothing changed in "app"`, for the flags as for the form.
- `dexily edit <query>` with no field flags opens a full-screen form, in a terminal: the description, the tags as one comma-separated line, and one row per property, name beside value. Tab and Shift+Tab (or ↓ and ↑) move between boxes; Enter saves, except in a property's name, where it moves on to the value; Esc cancels, except on a property row, where it steps back out of the properties first; Ctrl+C cancels too. Ctrl+N adds a property and Ctrl+D deletes one after asking `y/n`; a row left with both boxes empty disappears. Only the fields you changed are sent, so retyping a tag or a property name in another case is no change; saving with nothing changed writes nothing and says `nothing changed`. The form draws on stderr and puts the terminal back however it ends, a crash included. Piped or under `--json` there is no form, and a bare `edit` stays a usage error, exit 2.
- `dexily config form-wrap on|off` sets whether Tab and Shift+Tab wrap around at the ends of `edit`'s form, as the app's Tab order does; on by default, and `--reset` goes back to it.
- `dexily restore <query>` brings a project back from the bin, and `dexily purge <query>` deletes a binned project's record for good. Both look only in the bin — the live list leaves binned projects out, so they could not otherwise find the project they act on — and say so when nothing there matches: `no project in the bin matches "app"`. A project is binned when its folder is deleted from disk, so `restore` recovers the record and not the files. `purge` cannot be undone and asks first, as `untrack` does; `--yes` answers in advance, and with stdin piped it refuses without it.
- `dexily edit <query> --set <key=value> --unset <key>` sets and removes a project's properties. `--set` splits at the first `=`, so a value may contain `=` or commas, and keeps the value exactly as typed; both flags repeat. Names match ignoring case, as the search bar matches them, so `--unset client` removes a `Client` set in the app and `--set client=x` replaces it rather than adding a second one. A `--set` with no `=` is rejected before anything is looked up.
- `dexily edit <query> --add-tag <tags> --remove-tag <tags>` adds and removes tags without retyping the rest. Both repeat or take commas; a removal ignores case, so `--remove-tag rust` removes `Rust`; removing a tag the project lacks is not an error; and removals apply before additions. Given together with `--description`, everything is saved in one write.
- `dexily edit <query> --description <text>` changes a project's description; `--description ""` clears it. `edit` is where every field that takes a value goes, so tags and properties join it as flags; with none given it is a usage error rather than a write that changes nothing.
- `dexily favorite <query>` and `dexily unfavorite <query>` set and clear a project's favourite flag — the CLI's first write beyond adding and untracking, and the pair to `list --view favorites`. They find the project the way `show` does and take `-t/--tracker` likewise. Two verbs rather than a flag on an edit command: a state change with no value is a verb, which also lets the planned TUI bind a key to it.
- The project table gains an ID column — the first 8 characters of each project's id, the shortest prefix `show` accepts — so a row can be copied from by id as well as by `parent/folder`.
- `dexily list --view <set>` draws from `all` (the default), `favorites` or `binned`. One flag with a value rather than a `--favorite` and a `--binned` flag, because the sets are alternatives — and because the GUI already models them as one `View` type with groups as a further case. Binned projects appear under `binned` and nowhere else: favouriting is stored independently of binning, so a favourited project that is binned leaves `favorites` and returns on restore. An empty view now says which emptiness it is — `the bin is empty`, `no favourites yet` — rather than always claiming nothing is tracked.
- `dexily list --sort <field>` orders the table by `name` (A to Z) or `last-opened` (most recent first), with `-r/--reverse` to flip it. Each field has its own natural direction, so `--reverse` means "the opposite of this field", not "descending" — `--sort last-opened` answers most-recent-first, and only `--sort last-opened --reverse` reaches for the stalest.
- `dexily show` reports the group a project belongs to. Ungrouped projects show no group line at all, the way a tracker section a project lacks is skipped rather than printed empty.
- `dexily add [dir]` starts tracking a directory, defaulting to the current one — `dexily add` inside a project folder is the common case. The path is resolved to an absolute one before it is stored, so `add .` and `add ../app` record where they actually point; a path that does not exist, or that is a file, is refused. A directory that is already tracked is reported as such rather than duplicated or treated as an error.
- `dexily open <query>` opens a project in its application — the one in `open_with`, or the system default — and records that it was opened. A directory that has been deleted or moved, or an `open_with` app that is no longer installed, is reported before anything is launched.
- `dexily untrack <query>` forgets a project's metadata and leaves its directory on disk alone. It asks for confirmation first; `--yes` answers in advance, and with stdin piped it refuses rather than reading a script's input as consent. Answering no prints `cancelled` and exits 0.
- `dexily list` prints tracked projects as a bordered table — name, `parent/folder`, trackers, last opened — that fills at least 70% of the terminal and sits centred in it.
- `dexily scan <dir>` walks a folder for projects and prints what it found — directory, the name it would get, what matched, and whether it is already tracked — registering nothing. `--import` performs the registration as a second run, `--depth <n>` looks further than the immediate children, `--include-ignored` looks inside `node_modules`, `target` and dot-directories, and `-t/--tracker` restricts the detectors. A walk that hits the 50,000-directory limit says so rather than reading as an empty disk, and a row that fails to import is reported without failing the command.
- `--tracker <kind>` (short `-t`) on `list` and `show` keeps only the projects carrying that tracker, before the query is matched — so `show app --tracker git` finds the git `app` where `show app` alone reports several matches. `git` and `unreal` are the kinds; anything else is rejected with the list of valid ones. Name several by repeating the flag or with commas (`-t git,unreal`), and a project carrying any of them is kept.
- With `--tracker`, the table's TRACKERS column becomes those trackers' own columns — BRANCH and CHANGES for git, ENGINE for Unreal — in the order asked for, with `-` where a project lacks a kind. `show` gains a section per kind under the project's details: branch, changes and remote for git; project, engine and source control for Unreal.
- `dexily list <query>` lists only the projects whose name contains the query — the exact name first, then names starting with it, then the rest — or, for a query with a `/` like `work/app`, whose path ends with it. Nothing matching prints `no projects match "…"` and exits 0.
- `dexily config folder-color` and `dexily config header-color` set the colour of each project's folder name and of the table's header row; `--folder-color` and `--header-color` override them for one run.
- `--json` failures: under `--json`, a failed command writes `{"schema": 1, "error": {"kind", "message", …}}` to stderr instead of prose. `show` reports `not_found`, or `ambiguous` with the matching projects; anything else is `error`. The format is documented for scripts and LLM agents in `docs/cli/agents.md`.
- `dexily show <query>` shows one project: an exact name first, then a full id or an id prefix of 8 or more characters, then a `parent/folder` path ending, then part of a name (ignoring case). When several match, it prints a table of them — name, `parent/folder`, trackers, last opened — and exits 1.

### Changed

- `show`, `open` and `untrack` resolve their query through one shared `find_one`, so the same query finds the same project whichever verb is in front of it. `open` and `untrack` accept `-t/--tracker` for the same reason `show` does.
- `--json` writes each tracker as `{"kind": "git", …its fields}` instead of `{"Git": {…}}`.
- When several projects match, `show` now says "multiple matches found, which one did you mean?" above the table.

### Fixed

- Tables are measured in screen columns rather than characters, so an emoji, an icon or a CJK name no longer pushes every column after it out of line.
