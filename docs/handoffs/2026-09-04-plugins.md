# Handoff — plugins (Spec 3)

**Date:** 2026-09-04
**Status:** partly ready. **UI plugins can start now** — they are data, and
nothing about them is blocked. Utility plugins with a frontend half are blocked
on a design decision, not on code.
**Prerequisite:** none in code. The seams exist.

This is the briefing for the plugin initiative, not its design. It also carries
the state of the tree as of the end of 2026-09-04, because several things
changed that day and the older documents were written before them.

The observer CLI remains the *next* initiative and has its own, deeper handoff at
[`2026-09-04-observer-cli.md`](2026-09-04-observer-cli.md). Nothing here
supersedes it. Plugins are the initiative after, and this document exists so the
reasoning behind them does not live only in a chat log.

---

## 1. The idea in one paragraph

Project Indexer should not be the thing that adds the next twenty project types.
A plugin is how somebody else adds one. There are two kinds, split by what a
plugin is *for*. A **UI plugin** changes how the app looks — theme and layout —
and is **data, not code**: a config file, the way a dotfile is. A **utility
plugin** changes what the app can do — a richer git experience, a new project
type — and ships as a backend half, a frontend half, or both. The split matters
because it decides the trust story: a config file has nothing to sandbox, a
backend plugin is ordinary dependency trust, and only a frontend half runs
somebody else's code inside the webview.

## 3. What you are building on

Four things already exist that make this cheaper than it looks.

**The theme is already a token system.** `src/app.css` declares the whole visual
language in a `@theme` block — `--color-void`, `--color-panel`, `--color-phos`,
`--color-accent`, the state hues, `--font-display` and `--font-mono`, and the
single 2px `--radius-*`. A theme plugin is an override set for those tokens, read
from a config file and applied as custom properties. Most of the work is reading
and validating a file, not restyling an app.

**The generic renderer already handles unknown trackers.** A tracker kind the UI
has never heard of renders today, without code changes: `src/lib/trackers.ts`
types fields by inference — `https://` becomes a link, `git@` becomes copyable
text rather than a broken link, `*_root` and `*_path` get open and reveal
buttons, arrays become chips — and `trackerColor(kind)` assigns a contrast-safe
hue from a hash of the name. `TrackerPanel.svelte` and `TrackerBadges.svelte` are
where that lands.

This matters more than it sounds. It means **a backend-only utility plugin is
already a complete contribution**, and it means the bar a frontend one has to
clear is "better than a decent generic field list", not "makes this visible at
all".

**The detector seam is real.** `Detector` is a two-method trait — `kind()` and
`detect(&Path)` — and `crates/core/src/detectors/registry.rs::default_detectors()`
is the single registration point. Detectors are independent and unordered by
design, so a Jujutsu repository colocated with a git one correctly reports both,
with no precedence rule to invent.

A seam is not a plugin API, though. `default_detectors()` returns a compile-time
`Vec<Box<dyn Detector>>`. Turning that into something a third party extends is
the design work, and §4 constrains how.

**Capabilities are already per-window.** `src-tauri/capabilities/default.json`
scopes its permissions to `"windows": ["main"]`. That is the hook for the second
containment layer in §4 — a second webview with its own, smaller capability set
is a configuration change plus a window, not new infrastructure.

## 4. Trust — it sorts by kind, not evenly

The useful consequence of splitting plugins by purpose is that only one of the
four categories is actually hard.

| Kind | What it is | What it can reach | Gated on |
|------|-----------|-------------------|----------|
| UI — theme, layout | a config file | nothing; it is data | nothing |
| Utility, backend | a crate, compiled in | full user privileges | dependency trust |
| Utility, frontend | JavaScript in the webview | everything `invoke` reaches | containment |
| Utility, both | both halves | as above | as above |

**A UI plugin has no trust problem because it has no code.** That property is
load-bearing, not incidental — it is the entire reason this category can ship
without waiting for anything below. Guard it: the moment a UI plugin can execute,
it has become a frontend utility plugin wearing a theme's clothes and inherits
everything in this section.

Two caveats that keep the claim honest:

- **"No code" removes code execution, not injection.** A token value interpolated
  unchecked into CSS could carry `;` and further declarations. Parse each value to
  its expected type — colour, length, font stack — and reject the rest.
- **A malformed config must not stop the app starting.** Fall back to the
  built-in values and surface the error in the UI. `PI-005` is the standing
  reminder that a startup failure is the one kind a user cannot work around.

**Frontend code is the hard case.** The frontend is a webview, and Tauri exposes
`invoke` to everything inside it; `invoke` reaches `delete_project_directory` and
the application launcher. There is no per-script permission within a webview, so
a plugin has exactly the powers the app has.

1. **A content security policy.** Stops a plugin fetching more code or phoning
   home. It does *not* stop it calling `invoke`. Necessary, not sufficient —
   **done**, see §2.
2. **Capability scoping.** Restrict which commands a window may call, and run
   plugins in their own webview with a reduced set. The first boundary that is
   enforced rather than agreed to. **Not built.**
3. **No `invoke` for plugins at all.** Plugins get a narrow host API —
   `host.tracker()`, `host.reveal(path)` — and never touch the command bridge.
   The most work, and the only version that is genuinely safe rather than merely
   awkward to abuse. **Not built.**

One of layers 2 or 3 must exist before any third-party frontend code loads. That,
and not the rendering, is what gates the frontend shapes.

**Native code cannot be contained, and cannot be made containable.** A Rust
plugin loaded into the process has the user's full privileges: no CSP applies to
it, no capability list constrains it, there is no sandbox, and nothing in Tauri
changes that because nothing can — it is the same machine code as the app.

The consequence is recorded in `ROADMAP.md` under *Considered and declined*: **a
runtime loader that picks up `.so`/`.dll` files from a folder should not be
built.** It would hand every plugin author arbitrary code execution on every
user's machine in exchange for a nicer install step. The model instead is source
distribution — a plugin is a crate, the user adds it and rebuilds, and trust is
established the way it is for any other dependency.

If you find yourself designing a dynamic loader because source distribution feels
inconvenient, that is the moment to stop and re-read this section.

## 5. Open design decisions — settle these in brainstorming

Nothing below is decided. They are split by which kind they block, because the
UI ones can be settled and shipped without touching the utility ones.

### UI plugins — small decisions, no blockers

1. **File format and location.** It has to be hand-editable, which argues for
   TOML over JSON (comments, and no trailing-comma traps). The app's config
   directory is the natural home, next to `projects.db` —
   `~/.config/com.shaer.project-indexer/` on Linux, the platform equivalent
   elsewhere. One file, or a directory of them with a selection setting?

2. **Which tokens are public.** Every `@theme` token is *technically* overridable,
   but publishing all of them makes the internal names a compatibility surface.
   A named, documented subset is probably right, with unknown keys ignored rather
   than rejected — the same forward-compatibility rule the `--json` contract uses.

3. **How far layout goes.** Named regions plus an ordering, sections toggled on
   and off, density — all declarative and fine. The line is anything that wants
   to compute what to render. Decide where it sits before someone asks for
   conditionals in a config file.

4. **Live reload, or restart?** Watching the file is friendlier and is a small
   amount of work; it is also a background file watcher, which is a new failure
   mode. Restart-to-apply is defensible for a first version.

### Utility plugins — one decision blocks the rest

5. **Is a frontend plugin a module the app imports, or a document in its own
   webview?** This is the blocking decision, and it is not reversible once an API
   is published. A module shares the app's realm and can reach the IPC bridge on
   its own, which makes a host API a convention rather than a boundary and rules
   layer 2 out entirely. Its own webview makes layer 2 available and enforced, at
   the cost of message passing instead of function calls, plus sizing, theming
   and focus for an embedded frame. **Settle this before anything else in this
   group** — layers, host API shape, and registration are all downstream of it.

6. **What does a plugin register against?** A tracker `kind` string is the obvious
   key, but kinds are just strings in a hash-coloured namespace today. Two plugins
   claiming `git` need an answer, and it should not be first-one-wins-silently.

7. **How does source distribution actually work for a Rust plugin?** A Cargo
   feature? A `plugins/` directory of path dependencies the user edits? A
   generated registry file? The honest requirement is that a non-Rust user can
   follow it, which argues for the least clever option available.

8. **Does a plugin get to persist anything?** `projects.db` is a cross-app
   contract — `devmon` attaches it read-only, and the `meta` table is part of that
   contract. A plugin writing to it is a schema-compatibility problem wearing a
   feature's clothes. Separate storage, no storage, or a namespaced table,
   decided deliberately.

9. **What does the JSON side look like?** Once trackers can come from plugins, the
   CLI's `--json` output carries kinds nobody has seen. The contract in
   `ROADMAP.md` already anticipates this — unknown kinds serialise rather than
   fail — but the plugin API should make producing a conforming tracker the easy
   path rather than something authors get right by luck.

10. **Is a frontend-only utility plugin worth it at all?** The generic renderer
    sets a decent floor, and backend-only plugins clear the bar with no
    containment work. If the first several plugins anyone actually wants are
    backend-only, the frontend path is polish bought at the price of the hardest
    problem on this page. Worth checking before paying for it.

## 6. Constraints and gotchas

- **`Tracker` is a closed enum today** — `Git(GitInfo)`, `Unreal(UnrealInfo)`.
  Every new project type widens it. A plugin producing trackers means this stops
  being closed, and that is a bigger change than it looks: it touches
  serialisation, the database, and the CLI contract at once.
- **`indexer-core` must not import Tauri.** The compiler enforces it. Any plugin
  machinery that belongs to the domain goes in core; anything that knows about
  webviews or `invoke` does not.
- **The app is the only writer of `projects.db`.** `devmon` reads it. Keep it
  that way, or the cross-app contract needs renegotiating first.
- **`style-src` still carries `unsafe-inline`**, because a few components compute
  colours into a `style` attribute — `trackerColor(kind)` in the tracker badges
  most of all. This matters directly for UI plugins: applying theme tokens means
  writing custom properties at runtime, which lands in the same permissive bucket.
  It is *not* a licence to skip per-value validation — the CSP is what stops a
  theme loading external resources, and validation is what stops one injecting
  declarations. Moving the computed colours to custom properties is the
  prerequisite for ever tightening this.
- **Commit trailer:** every commit ends with a `Co-Authored-By:` line naming the
  model that did the work. Name whichever model you are.
- **Install the pre-commit hook** before you start: `git config core.hooksPath
  .githooks`. It mirrors CI exactly and runs only the gates your staged files can
  affect.
- **Neither CI nor the hook launches the app.** `PI-005` compiled, passed every
  test, and still exited before showing a window. If your change touches startup
  or anything platform-specific, run the real thing.

## 7. Suggested route

The two kinds have different shapes of risk, so do not treat them as one project.

**Start with UI plugins.** They are unblocked, they are small, and they are the
only part of this initiative that can ship without a security design first. A
theme file that overrides `@theme` tokens, validated per value, falling back to
built-in values on anything malformed. That is a spec-sized piece of work, not an
architecture.

**Then backend-only utility plugins**, if the demand is real — a `Detector`
distributed as source, with whatever registration mechanism §5.7 settles on. Also
unblocked, and it is the shape that makes "somebody else adds the next project
type" actually true.

**Only then the frontend utility path**, and start with §5.5 rather than with
code. Prototype the boundary before the API: a second webview with a reduced
capability set rendering a hard-coded panel proves or kills layer 2 in an
afternoon, and it tells you which of the two API shapes you are committing to.

The tempting first step is a plugin that renders a nicer git panel, because the
data is right there. Resist it: that path builds the API before the boundary, and
the boundary is what constrains the API.

Brainstorm the §5 questions for whichever kind you are starting on, ending in a
spec at `docs/superpowers/specs/`. The UI half warrants a small one; the frontend
utility half warrants the full treatment.
