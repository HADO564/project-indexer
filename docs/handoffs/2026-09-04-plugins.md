# Handoff — plugins (Spec 3)

**Date:** 2026-09-04
**Status:** not ready to start. The trust design has to be settled first, and
that is a design problem rather than a coding one.
**Prerequisite:** none in code. The seams exist; what is missing is the decision
about what a plugin is allowed to do.

This is the briefing for the plugin initiative, not its design. It also carries
the state of the tree as of the end of 2026-09-04, because several things
changed that day and the older documents were written before them.

The observer CLI remains the *next* initiative and has its own, deeper handoff at
[`2026-09-04-observer-cli.md`](2026-09-04-observer-cli.md). Nothing here
supersedes it. Plugins are the initiative after, and this document exists so the
reasoning behind them does not live only in a chat log.

---

## 1. The idea in one paragraph

Project Indexer should not be the thing that adds the next twenty project types.
A plugin is how somebody else adds one. There are two shapes: a **UI plugin**
that renders data the backend already produces better than the generic renderer
does, and a **UI plugin paired with a Rust `Detector`** for anything the backend
cannot yet see — a Jujutsu plugin being the clean example, since it needs both a
reader for `.jj` and a panel to show what it found. The first shape is an
improvement on something that already works. The second is a new capability, and
it is the one with the hard problem attached.

## 3. What you are building on

Three things already exist that make the first shape cheaper than it looks.

**The generic renderer already handles unknown trackers.** A tracker kind the UI
has never heard of renders today, without code changes: `src/lib/trackers.ts`
types fields by inference — `https://` becomes a link, `git@` becomes copyable
text rather than a broken link, `*_root` and `*_path` get open and reveal
buttons, arrays become chips — and `trackerColor(kind)` assigns a contrast-safe
hue from a hash of the name. `TrackerPanel.svelte` and `TrackerBadges.svelte` are
where that lands.

This matters more than it sounds. It means **a backend-only plugin is already a
complete contribution**, and it means the bar a UI plugin has to clear is "better
than a decent generic field list", not "makes this visible at all".

**The detector seam is real.** `Detector` is a two-method trait — `kind()` and
`detect(&Path)` — and `crates/core/src/detectors/registry.rs::default_detectors()`
is the single registration point. Detectors are independent and unordered by
design, so a Jujutsu repository colocated with a git one correctly reports both,
with no precedence rule to invent.

A seam is not a plugin API, though. `default_detectors()` returns a compile-time
`Vec<Box<dyn Detector>>`. Turning that into something a third party extends is
the design work, and §4 constrains how.

**Capabilities are already per-window.** `src-tauri/capabilities/default.json`
scopes its permissions to `"windows": ["main"]`. That is the hook for the second
containment layer in §4 — a second webview with its own, smaller capability set
is a configuration change plus a window, not new infrastructure.

## 4. Trust — read this before designing the API

Both shapes run somebody else's code. They do not have the same containment
story, and the asymmetry decides how much of this is safe to build.

**A UI plugin is containable, in three layers.** The frontend is a webview, and
Tauri exposes `invoke` to everything inside it. `invoke` reaches
`delete_project_directory` and the application launcher. There is no per-script
permission within a webview: a plugin has exactly the powers the app has.

1. **A content security policy.** Stops a plugin fetching more code or phoning
   home. It does *not* stop it calling `invoke`. Necessary, not sufficient —
   **done**, see §2.
2. **Capability scoping.** Restrict which commands a window may call, and run
   plugins in their own webview with a reduced set. The first real boundary.
   **Not built.**
3. **No `invoke` for plugins at all.** Plugins get a narrow host API —
   `host.tracker()`, `host.reveal(path)` — and never touch the command bridge.
   The most work, and the only version that is genuinely safe rather than merely
   awkward to abuse. **Not built.**

One of layers 2 or 3 must exist before any third-party UI code loads. That, and
not the rendering, is the gate on shape one.

**A Rust plugin is not containable, and cannot be made so.** Native code loaded
into the process has the user's full privileges: no CSP applies to it, no
capability list constrains it, there is no sandbox, and nothing in Tauri changes
that because nothing can — it is the same machine code as the app.

The consequence is recorded in `ROADMAP.md` under *Considered and declined*: **a
runtime loader that picks up `.so`/`.dll` files from a folder should not be
built.** It would hand every plugin author arbitrary code execution on every
user's machine in exchange for a nicer install step. The model instead is source
distribution — a plugin is a crate, the user adds it and rebuilds, and trust is
established the way it is for any other dependency.

If you find yourself designing a dynamic loader because source distribution feels
inconvenient, that is the moment to stop and re-read this section.

## 5. Open design decisions — settle these in brainstorming

Nothing below is decided.

1. **Layer 2 or layer 3, and can you start with 2?** A reduced-capability webview
   is much less work than a host API and gives a real boundary. Is it enough to
   ship shape one, with layer 3 as a later tightening — or does starting at 2
   define an API surface you cannot walk back?

2. **What is a UI plugin, concretely?** A JavaScript module the app imports? A
   web component? A manifest plus an entry point? This determines everything
   about layer 2, because "run it in its own webview" is easy for an iframe and
   awkward for an imported module.

3. **What does a plugin register against?** A tracker `kind` string is the
   obvious key, but kinds are just strings from a hash-coloured namespace today.
   Two plugins claiming `git` need an answer, and it should not be
   first-one-wins-silently.

4. **How does source distribution actually work for a Rust plugin?** A Cargo
   feature? A `plugins/` directory of path dependencies the user edits? A
   generated registry file? The honest requirement is that a non-Rust user can
   follow it, which argues for the least clever option available.

5. **Does a plugin get to persist anything?** `projects.db` is a cross-app
   contract — `devmon` attaches it read-only, and the `meta` table is part of
   that contract. A plugin writing to it is a schema-compatibility problem
   wearing a feature's clothes. Separate storage, no storage, or a namespaced
   table, decided deliberately.

6. **What does the JSON side look like?** Once trackers can come from plugins,
   the CLI's `--json` output carries kinds nobody has seen. The contract in
   `ROADMAP.md` already anticipates this — unknown kinds serialise rather than
   fail — but the plugin API should make producing a conforming tracker the easy
   path rather than a thing plugin authors get right by luck.

7. **Is shape one even worth shipping alone?** The generic renderer sets a decent
   floor. If the first three plugins anyone actually wants are all shape two, the
   UI-only path is polish and the detector path is the product. Worth checking
   before building the easier half first because it is the easier half.

## 6. Constraints and gotchas

- **`Tracker` is a closed enum today** — `Git(GitInfo)`, `Unreal(UnrealInfo)`.
  Every new project type widens it. A plugin producing trackers means this stops
  being closed, and that is a bigger change than it looks: it touches
  serialisation, the database, and the CLI contract at once.
- **`indexer-core` must not import Tauri.** The compiler enforces it. Any plugin
  machinery that belongs to the domain goes in core; anything that knows about
  webviews or `invoke` does not.
- **The app is the only writer of `projects.db`.** `devmon` reads it. Keep it
  that way, or the cross-app contract needs renegotiating first.
- **`style-src` still carries `unsafe-inline`**, because a few components compute
  colours into a `style` attribute — `trackerColor(kind)` in the tracker badges
  most of all. If plugin CSS ever becomes a concern, moving those to custom
  properties is the prerequisite for tightening it.
- **Commit trailer:** every commit ends with a `Co-Authored-By:` line naming the
  model that did the work. Name whichever model you are.
- **Install the pre-commit hook** before you start: `git config core.hooksPath
  .githooks`. It mirrors CI exactly and runs only the gates your staged files can
  affect.
- **Neither CI nor the hook launches the app.** `PI-005` compiled, passed every
  test, and still exited before showing a window. If your change touches startup
  or anything platform-specific, run the real thing.

## 7. Suggested route

This is architectural and security-shaped, so it warrants the full treatment
rather than going straight to code.

1. **Brainstorm §5**, with §4 as a hard constraint rather than an input to be
   traded away. End in a spec at `docs/superpowers/specs/`.
2. **Prototype the boundary before the API.** A second webview with a reduced
   capability set, rendering a hard-coded panel, proves or kills layer 2 in an
   afternoon. Do that before designing anything a plugin author would see.
3. **Then** plan and execute, on a feature branch.

The tempting first step is a plugin that renders a nicer git panel, because the
data is right there. Resist it: that path builds the API before the boundary, and
the boundary is the part that constrains the API.
