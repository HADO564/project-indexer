## 1. How to work with this user — read before writing code

Current mode is **ship-first** (the earlier "user writes all the feature code,
learn-by-doing" rule is **paused** — see the session memory). So:

- **You (the agent) write the code.** Plan it, build it, test it, document it.
  The user reviews and directs; surface trade-offs and get a nod before large or
  outward-facing moves.
- **No Claude attribution** in commits or PRs — ever. No co-author/"generated by"
  lines.
- **PR per feature, CI green before merge.** `main` is protected. Open a PR,
  wait for CI (the real checks: `cla`, `frontend`, `plan`, `rust (ubuntu-22.04)`,
  `rust (windows-latest)`; the `skipping` dist/release jobs are tag-gated and
  normal). The user reviews; merge with a merge commit (repo convention).
- **Clean up merged branches** (delete the remote branch after merge) — the user
  likes this. Never touch `cla-signatures` (it's the CLA bot store, not merged).
- **Subagents for parallelizable work.** When tasks have **disjoint file
  scopes**, dispatch isolated-worktree workers, then integrate with cherry-picks
  and run the authoritative full-workspace verification yourself. Watch for one
  trap learned this session: if two workers must touch the same file (e.g. a
  shared enum, the git parser), do them **sequentially** or in one worker — do
  not parallelize onto the same file.

## 2. Where things stand

Shipped and on `main`:

- **The observer** — `dexily <cmd>` runs a recognized command and tracks what it
  made. Recognizers: `mkdir`, `git init`/`clone`/`worktree add`, `cargo new`/`init`,
  `go mod init`, `gh repo create`, the package/project managers' bare `init`
  (`npm`/`pnpm`/`yarn`/`poetry`/`uv`), `flutter create`, `deno init`, `zig init`.
  **Fail-closed** and **terminal-only override** (`run it anyway? [y/N]`); an
  overridden recognized-git line still tracks its repo. Code:
  `crates/cli/src/observe/`.
- **Detectors** — 18 project-type trackers (git, unreal, node, python, go, godot,
  unity, rust, cmake, maven, gradle, docker, php, ruby, dart, swift, elixir,
  dotnet), marker-file based. Code: `crates/core/src/detectors/`. New kinds must
  be added to the exhaustive (no `_` arm) matches in `crates/cli/src/output/human.rs`
  and the `TrackerKind` enum in `crates/cli/src/commands/mod.rs` — they won't
  compile otherwise, which is the safety net.
- **Config** `track-prompt`, the `-v`/`--verbose` (and `RUST_LOG`) logger that
  surfaces core's `log::warn!` diagnostics (silent by default), and the
  **Dexily** rename (productName/window/HTML title; bundle identifier kept, so
  the shared DB didn't move).
- **The `--json` contract** and the two living docs: the SUPPORTED page and
  `agents.md`. Keep both true when you change recognizers/detectors/output.

One release caveat: the app is now named **Dexily** but the last shipped release
(0.3.5) was built as `project-indexer_…`. The root `README.md` download table
still says `project-indexer_…` on purpose; flip it to `Dexily_…` **when the
first Dexily-named release is cut**, not before.

## 3. The next tasks (recommended order)

### A. The TUI — the headline milestone (CLI ROADMAP → *The TUI*; checklist §5)
Bare `dexily` opens a full-screen interface: panes (sidebar views + counts,
project list, detail), movement/search keybinds, a `:` command line parsed into
the **same `Command` enum** as the shell, letter shortcuts, a which-key action
menu built from the `Command` definitions, a `?` help overlay, and live refresh
via `PRAGMA data_version`. ratatui is already in use (the `edit` form, in
`crates/cli/src/tui/`).

**Prerequisite — do this first:** *prose-through-a-writer* (checklist milestone 3
item, and §5). Today dexily's human messages go straight to stderr (`eprintln!`
/ the `Voice` type). A TUI draws to an alternate screen, so a stray stderr line
lands on top of the interface and stays. The messages need to route through a
writer (or ride an `Outcome`) so the TUI can put them on its message line.
Nail this before building panes.

## 4. Invariants not to break

- **`dexily-core` has no Tauri dependency** — it's the shared backend for the
  CLI, the GUI, and any agent surface. Don't pull `tauri` into it.
- **The observer allowlist is a security boundary.** Only recognized commands
  run; options are fail-closed; the override is terminal-only; nothing that
  **downloads and runs** code is recognized (that's why `npm init <initializer>`,
  `npm create`, `npx`, `rails new` are refused/unrecognized). Changing the git
  parser (`recognizers.rs`) is the most delicate work — keep init/clone/worktree
  behavior and every refusal intact, and add tests.
- **Concurrent writers:** GUI + CLI both write the one SQLite file (WAL,
  `busy_timeout = 5000`). The planned "unchanged since I read it" `updated_at`
  check is in `docs/architecture.md` → *Quality backlog*. An agent server would
  make three writers — relevant if you touch agent access.
- Keep **`agents.md`** and the **SUPPORTED page** in step with any
  recognizer/detector/output change.
